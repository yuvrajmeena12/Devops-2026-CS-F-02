# Deliverable A: Executive Summary

## 1. Application Overview

**SkillSwap** is a full-stack, production-hardened peer-to-peer knowledge and skill barter platform. The core premise of the application is a zero-currency barter economy: users teach skills they have mastered in exchange for learning skills they desire from other verified community members.

Unlike traditional gig-economy or freelance tutoring marketplaces that depend on monetary payment gateways, escrow transactions, and hourly billing, SkillSwap treats skills as currency. Trust, accountability, and quality are maintained through an algorithmic matching engine, mutual session scheduling, a two-party cryptographic/database-confirmed completion protocol, and an earned reputation system culminating in an official "Verified Member" badge.

---

## 2. Major Functional Modules

The reference application is architected into 11 interconnected functional modules:

1. **Authentication & Session Security (`AUTH`)**:
   - Registration with mandatory 6-digit email OTP verification.
   - Dual-mode authentication: Password-based authentication with exponential brute-force lockout, and passwordless OTP login.
   - Self-service password recovery using two-phase OTP verification and single-use 64-character reset grant tokens.
   - Secure HttpOnly/SameSite cookies, JWT authentication with database-backed `tokenVersion` revocation, and account-level rate limiting.

2. **User Profile & Reputation Management (`USER`)**:
   - Comprehensive profile management: bios, detailed background, qualifications, hobbies, and achievements.
   - Secure image avatar uploading using byte sniffing (magic bytes) to prevent file-type spoofing, and automatic safe file removal.
   - Automated reputation calculation: average rating, rating count, completed swaps count, and auto-granting of the "Verified Badge" upon meeting strict thresholds (minimum 5 completed swaps with ≥ 3.5 average rating).

3. **Skill Catalog & Inventory (`SKILL`)**:
   - Two distinct skill listing categories per user: "Teach" (what the user offers) and "Learn" (what the user desires).
   - Strict taxonomy validation across 15 predefined industry categories and 4 proficiency tiers (`beginner`, `intermediate`, `advanced`, `expert`).
   - Authenticated proof document uploads (PDF/Images up to 5MB) attached exclusively to teaching skills.
   - Public landing platform metrics (`/api/public/overview`) and full server-side search, filtering, and pagination.

4. **Algorithmic Smart Matching (`MATCH`)**:
   - Real-time compatibility engine pairing users based on mutual skill intersection.
   - Automatic classification into **Reciprocal Matches** (User A teaches what User B wants AND User B teaches what User A wants) and **One-Way Matches** (unidirectional skill alignment).
   - Deterministic compatibility scoring incorporating reciprocal weight, skill count depth, verification badge status, and peer rating averages.

5. **Swap Proposal & Agreement Lifecycle (`SWAP`)**:
   - Formal bilateral swap proposals with optional reciprocal skill offering and introduction notes.
   - Collision protection enforcing at most one open/active swap proposal per requester/skill pair.
   - State-machine workflow: `pending` → `accepted` / `rejected` / `cancelled`.

6. **Scheduled Exchange Sessions (`SESS`)**:
   - In-app session coordination for accepted swaps with date/time pickers, UTC conversion, local time zone detection, and duration configuration (15–480 minutes).
   - Virtual meeting link integration (HTTPS Google Meet, Zoom, Teams, etc.).
   - Time-gated, two-party mutual completion protocol: neither party can mark a session complete before its start time, and a swap only transitions to `completed` once both participants independently confirm completion.

7. **Peer Reviews & Ratings (`REV`)**:
   - Post-completion feedback gated strictly to verified, completed swaps.
   - Mandatory 1-to-5 star integer rating and optional detailed qualitative testimonial.
   - Unique database constraint ensuring exactly one review per participant per swap.
   - Immediate automatic triggering of the reputation engine and badge verification evaluator.

8. **Direct Real-Time Messaging (`MSG`)**:
   - Bilateral communication between members using deterministic conversation keys (`minId:maxId`).
   - Paginated conversation list with unread counters, cursor-based historical message retrieval (`before`), and automatic message read marking.
   - Anti-spam rate limiting and debounced notification generation.

9. **In-App Notification Dispatcher (`NOTIF`)**:
   - Centralized asynchronous notification system supporting 10 event types.
   - Deduplication key mechanism preventing duplicate alerts for the same event.
   - Unread counters, mark single as read, and bulk mark-all-read operations with 90-day TTL expiration.

10. **Member Dashboard & Analytics (`DASH`)**:
    - Central command dashboard aggregating real-time KPI tiles (teach/learn counts, swap funnel, hours exchanged).
    - Dual interactive visual progress rings: Profile Readiness (5 specific milestones) and Road to Verified (5 required swaps).
    - Quick-access upcoming session widgets, smart match highlights, and recent activity timelines.

11. **Security & Infrastructure (`SEC`)**:
    - Recursive NoSQL injection prevention rejecting any keys containing `$` or `.`.
    - Strict Origin checking on state-changing requests to eliminate CSRF.
    - Tiered express rate limiting per IP and per account.
    - Defensive file streaming with strict Content Security Policy (`sandbox`, `default-src 'none'`) preventing malicious payload execution.

## 3. Actual Roles and Capabilities

The reference platform implements a clean, permission-enforced actor hierarchy:

| Role / Actor | Description & Capabilities |
| :--- | :--- |
| **Anonymous Visitor** | Can access the public landing page (`/`), view community totals (members, skills, completed swaps), browse recent teaching skill teasers, register for an account, log in, request passwordless OTPs, and initiate password resets. Restricted from all skill creation, explore directories, swaps, messaging, and profile views. |
| **Unverified Registered User** | Created an account via registration or attempted login, but has not submitted the valid 6-digit email OTP. Blocked by middleware from authenticated routes; redirected to `/verify-email`. |
| **Authenticated Member** | Verified member who can manage their profile, list up to 50 teaching and 50 learning skills, browse the full Explore directory, run Smart Match, propose swaps, schedule sessions, exchange messages, complete swaps, and leave reviews. |
| **Verified Badge Member** | An Authenticated Member who has earned the platform trust badge by achieving ≥ 5 completed swaps with ≥ 3.5 average peer rating. Receives visual badges across the UI, higher weighting in Smart Match scoring, and elevated community trust. |
| **Resource Owner** | The specific member who owns a skill, message, or swap proposal. Enforced server-side: only the owner can modify/delete skills or update profile details; only the target provider can accept/reject a swap request; only active participants can message each other or confirm session completion. |

```mermaid

```

## 5. Major Dependencies & Integrations

- **Runtime & Framework**: Node.js (≥18), Express 5.x.
- **Database & ODM**: MongoDB with Mongoose 9.x.
- **Client Frontend**: React 18, Vite, React Router 6, Axios.
- **Security & Cryptography**: `bcryptjs` (salt cost 12), `crypto` (timing-safe comparisons, HMAC-SHA256, secure random tokens), `jsonwebtoken` (HS256 with 7-day expiry), `helmet` (CSP & CORP), `cookie-parser`.
- **File Uploads**: `multer` with memory storage, custom buffer magic-byte sniffing (`pdf`, `png`, `jpg`, `webp`), atomic file system writes (`fs.promises`).
- **Communication & Mail**: `nodemailer` (supporting real SMTP or local console simulation via `DEV_LOG_OTP`).
- **Rate Limiting**: `express-rate-limit` with draft-7 headers and custom email/IP key generators.

## 6. Functional Gaps and Implementation Findings

During our static and structural reverse-engineering audit, the following key findings were identified:

1. **Complete Full-Stack Coverage**:
   - Every single backend route has an active controller, validator, and model backing.
   - Every frontend route and button connects to live API endpoints (no dummy mock buttons or simulated fake actions).
2. **Deterministic Smart Match without AI Overheads**:
   - The Smart Match engine is completely deterministic and built directly on MongoDB set queries and scoring mathematics—eliminating expensive LLM or vector database dependencies.
3. **Session Timing Gating**:
   - A participant cannot click "Mark Completed" until `session.scheduledAt` is in the past. This prevents premature confirmation exploitation.
4. **Rescheduling Behavior**:
   - Scheduling a new session automatically cancels any existing scheduled session for that swap, ensuring only one active appointment exists at a time.
5. **No Admin Panel in Scope**:
   - The application does not feature a dedicated administrative role (`admin`) or CMS moderation dashboard. Moderation relies on peer reviews, self-service skill removal, and strict input validation.

# MODULE 1: AUTHENTICATION & ACCESS SECURITY (`AUTH`)

---

### Feature ID: AUTH-01
**1. Feature name:** Account Registration with Email Verification OTP Dispatch  
**2. Purpose and business value:** Onboards new members into the barter community while ensuring valid contact details and email authenticity before granting system write permissions.  
**3. Availability and access:** Publicly accessible to anonymous visitors.  
**4. Entry points:** Frontend route `/register`, API endpoint `POST /api/auth/register`.  
**5. Preconditions:** Visitor must not already be signed in as an active verified user.  
**6. Inputs:** `name` (string, 2–60 chars), `email` (string, valid RFC email), `phone` (string, 7–15 digits), `password` (string, 8–72 chars), `confirmPassword` (string, exact match).  
**7. Validation and business rules:**
- `name`: 2 to 60 characters, trimmed of control characters.
- `email`: lowercased, validated by regex `/^[^\s@]+@[^\s@]+\.[^\s@]{2,}$/`, max 254 chars.
- `phone`: sanitized of spaces, hyphens, and parentheses; must match `/^\+?[0-9]{7,15}$/`.
- `password`: 8 to 72 characters, must include at least one letter and at least one digit. Must match `confirmPassword`.
- Uniqueness: If an account exists with this email and is verified, reject with 409 Conflict. If an account exists but is unverified, overwrite name, phone, and password hash (allows restarting unverified signups).  
**8. Exact execution workflow:**
1. User enters registration form fields and submits.
2. Frontend runs client validation; if invalid, displays inline field errors.
3. Client sends JSON payload to `POST /api/auth/register`.
4. Rate limiter (`authLimiter`) verifies IP threshold.
5. `rejectOperators` middleware validates payload against NoSQL operators.
6. Backend validator validates fields.
7. Password hashed with `bcryptjs` (salt cost 12).
8. Existing user check: if verified, return 409 Conflict; if unverified, update; otherwise create user with `emailVerified: false`.
9. OTP service generates 6-digit cryptographic code (`crypto.randomInt`), stores HMAC-SHA256 hash in `Otp` collection with 10-minute TTL, and sends email via SMTP (or prints in dev console).
10. HTTP 201 response returned with `{ email, verificationRequired: true, resendInSec }`.
11. Client navigates to `/verify-email` passing state.  
**9. Frontend behavior:** `Register.jsx` maintains touched/dirty states, real-time password strength meter, submits via Axios, redirects via `navigate('/verify-email', { state })`.  
**10. Backend behavior:** Handled by `authController.js:register`, validating via `validators/index.js`, hashing via `bcryptjs.hash(..., 12)`, calling `utils/otp.js:issueOtp`.  
**11. Database behavior:** Reads and upserts into `User` collection; creates or upserts into `Otp` collection (`{ email, purpose: 'signup' }`).  
**12. External dependencies:** `nodemailer` (or JSON console transport when SMTP is unset).  
**13. Output and side effects:** User record created (unverified), OTP record created, email dispatched, HTTP 201 JSON response.  
**14. State transitions:** User state: [None] → `emailVerified: false`.  
**15. Error and edge-case behavior:** Email collision returns 409 Conflict; invalid fields return 400 with structured `fields` map; rate exceeded returns 429.  
**16. Security requirements:** Salt cost 12, password masked in logs, NoSQL injection guard, rate limited.  
**17. Dependencies on other features:** OTP generation service (`utils/otp.js`).  
**18. Implementation evidence:** `backend/controllers/authController.js:35-56`, `backend/routes/authRoutes.js:8`.  
**19. Implementation status:** Fully implemented and verified.  
**20. Replication requirements:** Exact regex matching, bcrypt cost 12, unverified account overwrite handling, and return of cooldown seconds.

### Feature ID: AUTH-02
**1. Feature name:** Registration Email OTP Verification  
**2. Purpose and business value:** Confirms ownership of the provided email address, activates the account, and immediately signs in the member.  
**3. Availability and access:** Anonymous or unverified users possessing a valid signup OTP.  
**4. Entry points:** Frontend route `/verify-email`, API endpoint `POST /api/auth/verify-email`.  
**5. Preconditions:** Account must exist in `User` with `emailVerified: false`, active OTP record in `Otp` with `purpose: 'signup'`.  
**6. Inputs:** `email` (string), `otp` (6-digit numeric string).  
**7. Validation and business rules:**
- `otp` must be exactly 6 numeric digits `/^[0-9]{6}$/`.
- Attempts limited to 5 (`OTP_MAX_ATTEMPTS`). After 5 incorrect attempts, OTP document is locked.
- Single-use consumption: upon verification, `codeHash` is atomically set to `'used'` to prevent replay.  
**8. Exact execution workflow:**
1. User enters 6-digit code into `OtpForm`.
2. Client submits `POST /api/auth/verify-email`.
3. Backend fetches `Otp` document for email and purpose `'signup'`.
4. Checks expiry (`expiresAt < new Date()`) and lock status.
5. Verifies code using `crypto.timingSafeEqual` over HMAC-SHA256 hashes.
6. Atomically updates OTP record to `codeHash: 'used'`.
7. Updates `User` setting `emailVerified: true`.
8. Generates JWT signed with `tokenVersion` and sets `skillswap_token` HttpOnly cookie.
9. Returns HTTP 200 with sanitized private user object.

### Feature ID: AUTH-04
**1. Feature name:** Password Login with Exponential Brute-Force Lockout  
**2. Purpose and business value:** Authenticates members securely while protecting against credential-stuffing and password brute-force attacks.  
**3. Availability and access:** Anonymous visitors.  
**4. Entry points:** Frontend route `/login`, API endpoint `POST /api/auth/login`.  
**5. Preconditions:** Registered and email-verified account.  
**6. Inputs:** `email` (string), `password` (string).  
**7. Validation and business rules:**
- `email`: valid format. `password`: non-empty string.
- Account lockout: 5 free failed attempts (`LOGIN_FREE_ATTEMPTS`). On 6th attempt onwards, locks account for `min(15 mins, 30s * 2^(failed - 5))`.
- If account is locked, rejects with 429 Too Many Requests specifying wait time in seconds.
- Dummy password hash comparison (`DUMMY_HASH`) executed if account does not exist to eliminate timing discrepancies.
- If user exists but is unverified, login is denied with HTTP 403 `EMAIL_NOT_VERIFIED`, and a fresh signup OTP is automatically issued.  
**8. Exact execution workflow:**
1. User submits login form.
2. Checks `lockUntil > new Date()`; if locked, throws 429.
3. Compares password against `user.passwordHash` using `bcrypt.compare`.
4. If mismatch or user missing: increments `failedLogins`, computes exponential lockout timestamp if over threshold, and throws 401.
5. If verified matches: resets `failedLogins: 0, lockUntil: null`.
6. Issues JWT and sets HttpOnly cookie.
7. Returns HTTP 200 with private user payload.  
**9. Frontend behavior:** `Login.jsx` catches `EMAIL_NOT_VERIFIED` code and redirects directly to `/verify-email`.  
**10. Backend behavior:** Handled by `authController.js:login`, rate limited by both IP and email key generators.  
**11. Database behavior:** Reads `User` including `+passwordHash`, updates failed attempts and lock status.  
**12. External dependencies:** None.  
**13. Output and side effects:** Sets `skillswap_token` cookie; resets failed login counter on success.  
**14. State transitions:** `failedLogins` incremented or cleared; `lockUntil` set or cleared.  
**15. Error and edge-case behavior:** Returns 401 for bad credentials; 429 for account lockout; 403 for unverified email.  
**16. Security requirements:** Timing-equal dummy hash, exponential backoff, HttpOnly SameSite cookie.  
**17. Dependencies on other features:** `middleware/auth.js:setAuthCookie`.  
**18. Implementation evidence:** `backend/controllers/authController.js:83-125`.  
**19. Implementation status:** Fully implemented and verified.  
**20. Replication requirements:** Implement exponential backoff formula `baseLockSec * 2^over`, dummy hash comparison, and automatic unverified redirect.

### Feature ID: MATCH-01
**1. Feature name:** Algorithmic Smart Match Synergy Engine  
**2. Purpose and business value:** Automatically computes high-compatibility peer learning pairs across the community based on intersecting skill offerings and learning wishlists.  
**3. Availability and access:** Authenticated members.  
**4. Entry points:** Called internally by `matchController.js` and `dashboardController.js`.

**6. Inputs:** `userId`.  
**7. Validation and business rules:**
- Matches calculated from exact normalized skill names (`nameLower`).
- Identifies **theyTeachMe**: skills other users teach that match my learning wishlist.
- Identifies **iTeachThem**: skills other users want to learn that match my teaching list.
- Classification:
  - `reciprocal`: `theyTeachMe.length > 0 && iTeachThem.length > 0`
  - `they_teach_you`: `theyTeachMe.length > 0 && iTeachThem.length === 0`
  - `you_teach_them`: `theyTeachMe.length === 0 && iTeachThem.length > 0`
- Compatibility Scoring Formula:
  $$\text{Score} = (\text{isReciprocal} ? 100 : 40) + \min(\text{theyTeachCount}, 3) \times 8 + \min(\text{youTeachCount}, 3) \times 8 + (\text{isVerified} ? 6 : 0) + \min(\text{ratingAvg}, 5)$$
- Results sorted descending by score. Cached for 30 seconds.  
**8. Exact execution workflow:**
1. Loads user's teach and learn skill names.
2. Queries other users teaching what I want or learning what I teach (capped at 300 candidates).
3. Groups candidates in a map by user ID.
4. Queries user profiles for verified status, ratings, and avatar.
5. Computes score and compatibility classification.
6. Returns sorted matches array.  
**9. Frontend behavior:** Powers the top match highlight on Dashboard and full cards on Smart Match page.  
**10. Backend behavior:** Handled in `matchController.js:computeMatches`.  
**11. Database behavior:** Reads `Skill` and `User` collections.  
**12. External dependencies:** In-memory cache.  
**13. Output and side effects:** Scored match objects array.  
**14. State transitions:** None.

### Feature ID: SESS-04

**2. Purpose and business value:** The core trust mechanism ensuring a swap is only marked completed when the scheduled start time has passed and both partners independently confirm the exchange took place.  
**3. Availability and access:** Participants of a scheduled session.

- Time-gating: `session.scheduledAt.getTime() <= Date.now()`. If start time has not arrived, throws 403 Forbidden: `"You can mark a session complete once its start time has passed"`.
- Idempotent confirmation: adds caller's ID to `SwapRequest.completionConfirmedBy` using MongoDB `$addToSet`.
- First confirmation: swap transitions to `status: 'in_progress'`, counterpart receives notification `"User marked the session done. Confirm to finish the swap."`.
- Second confirmation: both participants confirmed. Swap transitions to `status: 'completed'`, `completedAt: new Date()`; session updated to `status: 'completed'`; reputation recomputed for both participants; both participants receive completion notification encouraging reviews.  
**8. Exact execution workflow:**
1. Verifies participant and scheduled status.
2. Verifies `scheduledAt <= Date.now()`.
3. Adds caller ID to `completionConfirmedBy`.
4. Evaluates if both IDs are present.
5. If only one: sets swap to `in_progress`, notifies partner, returns `{ swapStatus: 'in_progress', awaitingOther: true }`.
6. If both: sets swap to `completed`, sets session to `completed`, triggers `recomputeReputation` on both, notifies both, returns `{ swapStatus: 'completed', awaitingOther: false }`.  
**9. Frontend behavior:** `MySwaps.jsx` disables button and shows tooltip if time hasn't arrived; shows `"Waiting for partner to confirm"` alert after first confirmation.  
**10. Backend behavior:** Handled by `sessionController.js:complete`.  
**11. Database behavior:** Updates `SwapRequest`, `Session`, and calls `recomputeReputation`.  
**12. External dependencies:** Notification and reputation services.  
**13. Output and side effects:** Completion confirmation recorded; on dual confirmation, unlocks peer reviews and recalculates badges.  
**14. State transitions:** `scheduled` → `in_progress` (single confirm) → `completed` (dual confirm).  
**15. Error and edge-case behavior:** Premature click returns 403 Forbidden. Duplicate click is idempotent via `$addToSet`.  
**16. Security requirements:** Time gating and two-party cryptographic consensus prevent single-user rating fabrication.  
**17. Dependencies on other features:** `utils/reputation.js`, `utils/notify.js`.  
**18. Implementation evidence:** `backend/controllers/sessionController.js:169-225`.  
**19. Implementation status:** Fully implemented and verified.

## Workflow 1: User Onboarding, OTP Verification, and Profile Initialization

This journey represents the entry funnel from initial visitor registration to active, verified membership.

```mermaid
sequenceDiagram
    autonumber
    actor User as Visitor / Member
    participant Client as React Client (Vite)
    participant API as Express API
    participant DB as MongoDB
    participant SMTP as Mailer / Console

    User->>Client: Enters Name, Email, Phone, Password on /register
    Client->>Client: Validates form regex & password strength
    Client->>API: POST /api/auth/register
    API->>API: rateLimit + rejectOperators + validation
    API->>DB: Check User exists by email
    alt User exists & verified
        API-->>Client: 409 Conflict ("Account already exists")
    else User exists & unverified
        API->>DB: Update unverified user with new hash & details
    else New User
        API->>DB: Insert User (emailVerified: false)
    end
    API->>API: Generate 6-digit random code
    API->>DB: Upsert Otp (purpose: 'signup', codeHash: HMAC)
    API->>SMTP: Dispatch verification email
    API-->>Client: 201 Created { email, resendInSec, devOtp }
    Client->>Client: Navigate to /verify-email
    User->>Client: Enters 6-digit OTP code
    Client->>API: POST /api/auth/verify-email { email, otp }
    API->>DB: Atomically check and mark Otp as 'used'
    API->>DB: Update User (emailVerified: true)
    API->>API: Sign JWT with tokenVersion
    API-->>Client: 200 OK + Set-Cookie: skillswap_token
    Client->>Client: AuthContext stores user & redirects to /skills
```

### Branches, Failures, and Recovery Paths:
1. **Unverified Account Recovery**: If a user previously registered but closed the browser before entering the OTP, submitting `/register` again updates their credentials and issues a fresh OTP without error.
2. **Brute-Force OTP Lockout**: Entering 5 invalid OTP attempts locks the OTP document with HTTP 429 (`OTP_LOCKED`). The user must click "Resend Code" to reset the attempt counter.
3. **Resend Cooldown**: Clicking resend before 60 seconds have elapsed is blocked client-side by `useCountdown` and enforced server-side by checking `lastSentAt`.

## 2. Authentication Architecture

### 2.1 Token & Session Delivery Strategy
- **Token Format**: Standard JSON Web Token (JWT) signed using the HMAC-SHA256 (`HS256`) algorithm with a mandatory high-entropy secret (`JWT_SECRET`, minimum 32 characters checked at server boot).
- **Token Claims**:
  ```json
  {
    "sub": "64f1a2b3c4d5e6f7a8b9c0d1",  // MongoDB User ObjectId as string
    "tv": 0,                             // Token Version integer
    "iat": 1697414400,
    "exp": 1698019200                   // Expires in 7 days (JWT_EXPIRES_DAYS)
  }
  ```
- **Storage & Transport Mechanism**: Sent exclusively via an **`HttpOnly` Cookie** named `skillswap_token`.
  - `httpOnly: true` (strictly inaccessible to client JavaScript / `document.cookie`).
  - `secure: config.isProd` (enforces HTTPS in production environments).
  - `sameSite: 'lax'` (protects against cross-site request forgery while preserving top-level navigation).
  - `path: '/'` (available across all application routes).
  - `maxAge: 7 * 24 * 60 * 60 * 1000` (7 days).

### 2.2 Instant Revocation via `tokenVersion`
Unlike stateless JWT implementations that cannot be invalidated before expiration, SkillSwap implements stateful token revocation through the `User.tokenVersion` field:
1. Every JWT embeds the user's current `tokenVersion` (`tv`).
2. The authentication middleware (`loadUserFromRequest`) caches user records for 60 seconds (`auth:user:${sub}:${tv}`).
3. Whenever a security event occurs (e.g. Password Reset via `AUTH-08`, Password Change via `AUTH-09`), the backend runs:
   ```javascript
   $inc: { tokenVersion: 1 }
   ```
4. Any JWT carrying the old `tv` integer is instantly rejected with HTTP 401 Unauthorized upon its next API call, immediately signing out compromised devices globally.

## 4. Cross-Cutting Security Middleware

### 4.1 NoSQL Operator Injection Guard (`rejectOperators`)
Attackers often attempt NoSQL injection by passing objects containing MongoDB query operators (e.g. `{"email": {"$ne": null}}` or `{"$gt": ""}`).
SkillSwap implements recursive inspection on both `req.body` and `req.query`:
```javascript
// backend/middleware/security.js:5-15
function hasUnsafeKeys(value, depth = 0) {
  if (depth > 6) return true;
  if (Array.isArray(value)) return value.some((v) => hasUnsafeKeys(v, depth + 1));
  if (value && typeof value === 'object') {
    for (const key of Object.keys(value)) {
      if (key.startsWith('$') || key.includes('.') || key === '__proto__' || key === 'constructor') return true;
      if (hasUnsafeKeys(value[key], depth + 1)) return true;
    }
  }
  return false;
}
```
Any request containing `$`, `.`, `__proto__`, or `constructor` is rejected outright with HTTP 400 Bad Request.

### 4.2 Cross-Origin Request Validation (`sameOrigin`)
To provide defense-in-depth for cookie authentication:
```javascript
// backend/middleware/security.js:42-47
function sameOrigin(req, res, next) {
  if (['GET', 'HEAD', 'OPTIONS'].includes(req.method)) return next();
  const origin = req.get('origin');
  if (origin && !isAllowedOrigin(origin)) throw forbidden('Request origin not allowed');
  next();
}
```
All state-changing HTTP requests (`POST`, `PUT`, `PATCH`, `DELETE`) require an Origin header matching `CLIENT_ORIGIN` (or localhost in development).

## 2. In-Depth Discrepancy & Gap Analysis

### 2.1 Absence of Administrative & Moderation Backoffice (Architectural Gap)
* **Observed State**: The database and user models do not maintain an `isAdmin` or `role: 'admin' | 'moderator'` field. All users have equal privilege boundaries scoped strictly to their own entity IDs.
* **Functional Consequence**: 
  - There is no administrative mechanism to suspend a malicious user, delete inappropriate skills, or moderate offensive messages/reviews.
  - Dispute resolution during session or swap disagreements relies on non-completion or mutual cancellation.
* **Replication Implication**: If the destination platform targets enterprise or commercial usage, an administrative role layer and moderation dashboard must be planned as an intentional extension.

### 2.2 Messaging: Polling Architecture vs. Real-Time WebSockets
* **Observed State**: The messaging engine (`/api/messages/:swapId`) is built on REST HTTP queries. Real-time updates in the UI (`frontend/src/pages/Messages.jsx` or chat components) operate on periodic interval polling (or user-driven refreshes) rather than WebSocket/Socket.io subscriptions.
* **Functional Consequence**: 
  - Server load increases with high active concurrent chat sessions.
  - Message delivery latency is bounded by the polling cycle.
* **Replication Implication**: In a modern production deployment, replacing or augmenting the REST endpoints with a WebSocket / WebRTC signaling server is recommended, while preserving the existing database storage and conversation authorization rules.

### 2.3 Email Delivery Engine: SMTP vs. Console Logging Fallback
* **Observed State**: In `backend/src/utils/mailer.js`, when environment variables `SMTP_HOST`, `SMTP_USER`, and `SMTP_PASS` are absent, the mailer defaults to logging OTP verification codes directly to `console.log` and resolves cleanly with `true`.
* **Functional Consequence**: Enables instant local developer onboarding without external third-party mailer setup, but presents an operational security issue if deployed to production without explicit SMTP configuration.
* **Replication Implication**: The destination system must enforce strict environment validation on startup (fail-fast) if deployed in a production environment.

### 2.4 Session Video Calling Mechanism
* **Observed State**: The `Session` model accepts a `meetingLink` string (validated as an HTTPS URI). 
* **Functional Consequence**: SkillSwap does not embed a native WebRTC media streaming server or SFU (Selective Forwarding Unit). Users supply links to Google Meet, Zoom, Jitsi, or Microsoft Teams.
* **Replication Implication**: Exactly matches design expectations for an agnostic peer-to-peer session manager. Destination projects can either retain the external link model or integrate Daily.co/Twilio/LiveKit.

### 2.5 Active Swap Skill Deletion Safety Guard
* **Observed State**: `SkillController.deleteSkill` checks if the skill ID is referenced in any `SwapRequest` with status in `['pending', 'accepted', 'scheduled', 'in_progress']`. If found, HTTP 400 is returned with a descriptive error.
* **Functional Consequence**: Prevents orphan reference bugs where an ongoing swap references a non-existent skill document.
* **Status**: Fully implemented, verified, and mandatory for replication.

## 2. Complete Module Dependency Graph & Implementation Sequence

To ensure zero blocking dependencies and clean architectural layering, implement modules in this exact order:

### Stage 1: Identity, Auth & User Management (Days 1–3)
1. **Core User Entity & Security**: Email uniqueness, password hashing (Argon2 or bcrypt salt rounds $\ge 12$), `tokenVersion` integer for instant single-click session revocation across all client devices.
2. **OTP Verification Cycle**: Cryptographically secure 6-digit OTP, 10-minute expiry, single-use invalidation, cooldown rate limiting.
3. **Profile & Avatar Management**: Secure binary file validation, size limits (max 2MB), static serving with proper MIME headers.

### Stage 2: Skill Catalog & File Proof Processing (Days 4–5)
1. **Skill Model**: Categorization (`tech`, `language`, `arts`, `fitness`, `business`, `academics`, `other`), proficiency levels (`beginner`, `intermediate`, `advanced`), offering types (`offer`, `seek`).
2. **Safety Guard on Skill Removal**: Inability to delete or mutate active skills participating in ongoing swaps.
3. **Skill Proof Documents**: Multi-format support (PDF, PNG, JPG, WEBP), magic-byte validation, sandboxed file serving (`Content-Security-Policy: default-src 'none'; sandbox`).

### Stage 3: Matchmaking Engine & Skill Discovery (Days 6–7)
1. **Catalog Search & Filtering**: Multi-field text index over title/description, case-insensitive keyword search, category & level filtering, pagination (`page`, `limit`).
2. **Deterministic Smart Match Scoring Algorithm**: Exact mathematical reproduction of reciprocal and complementary score weighting.

### Stage 4: Swap Request Lifecycle & Session Management (Days 8–10)
1. **Swap Request State Machine**: `pending` $\rightarrow$ `accepted` $\mid$ `rejected` $\mid$ `cancelled` $\rightarrow$ `scheduled` $\rightarrow$ `completed`.
2. **Participant Validation**: Rejection of self-swaps, validation that requester owns `requesterSkillId` and target user owns `targetSkillId`.
3. **Session Scheduling**: Future timestamp verification, HTTPS meeting link validation, automatic invalidation of prior sessions upon rescheduling.
4. **Dual Two-Party Completion Protocol**: Atomic `$addToSet` recording of completion votes, strict enforcement of `session.scheduledAt <= Date.now()`.

### Stage 5: Reputation, Reviews & Real-Time Comms (Days 11–13)
1. **Review & Rating Submission**: Mutual review eligibility (only participating users on `status: completed` swaps), 1–5 integer rating, automatic reputation recalculation.
2. **Verified Member Badge Calculation**: Automated badge elevation at $\ge 5$ completed reviews with average rating $\ge 3.5$.
3. **Contextual Messaging Engine**: Swap participant scoping, message persistence, sequential ordering, pagination.
4. **Notification Dispatcher & Dashboard Aggregator**: Real-time event notifications and summary counters.

## 3. Immutable Business Rules That Must Remain Identical

The destination codebase must adhere strictly to these non-negotiable business rules:

### Rule 1: The Deterministic Matchmaking Formula
For any user $A$ viewing match candidate $B$:
$$\text{Score} = (\text{isReciprocal} \times 60) + 40 + \min(N_{\text{theyTeach}}, 3) \times 8 + \min(N_{\text{youTeach}}, 3) \times 8 + (\text{isVerified} \times 6) + \min(\bar{R}, 5)$$
* Where:
  - $\text{isReciprocal} = 1$ if $B$ offers a skill in $A$'s `seek` list AND $B$ seeks a skill in $A$'s `offer` list; otherwise $0$.
  - Base score is $100$ for reciprocal, $40$ for one-way complementary.
  - $N_{\text{theyTeach}}$: Count of skills candidate offers that match user's seek categories (capped at 3).
  - $N_{\text{youTeach}}$: Count of skills user offers that match candidate's seek categories (capped at 3).
  - $\text{isVerified}$: $1$ if candidate has `isVerified: true`, else $0$.
  - $\bar{R}$: Candidate's average rating (0 to 5.0).

### Rule 2: Two-Party Time-Gated Completion Protocol
A swap transitions to `completed` **only when**:
1. At least one session was scheduled.
2. `session.scheduledAt <= CurrentTime` (cannot mark complete in advance).
3. Both `requesterId` and `targetUserId` have submitted their completion confirmation (`completionConfirmedBy` array contains both unique user IDs).
4. When the second confirmation is recorded:
   - `SwapRequest.status` changes to `'completed'`.
   - `Session.status` changes to `'completed'`.
   - Completion notifications are triggered for both parties.

### Rule 3: Verified Badge Promotion Engine
The `User.isVerified` boolean attribute is automatically computed and updated whenever a new review is posted:
$$\text{isVerified} = (\text{ratingCount} \ge 5) \land (\text{ratingAvg} \ge 3.5)$$
where `ratingCount` and `ratingAvg` are calculated strictly from reviews attached to completed swaps.

### Rule 4: Active Swap Skill Deletion Immutability
A skill record cannot be deleted or purged if it is referenced as `requesterSkillId` or `targetSkillId` in any swap with status:
$$\text{status} \in [\,\text{'pending'},\, \text{'accepted'},\, \text{'scheduled'},\, \text{'in_progress'}\,]$$

### Rule 5: Token Invalidation via Version Tracking
All issued JWT access tokens must embed `tokenVersion: user.tokenVersion`.
- On password change or global logout, increment `user.tokenVersion += 1`.
- Authentication middleware must verify that `payload.tokenVersion === dbUser.tokenVersion`. If mismatched, immediately return HTTP 401 Unauthorized.

### Rule 6: Magic-Byte Binary Sniffing for Uploads
Never trust client MIME headers or file extensions. The server must validate the first bytes of incoming files:
- **PNG**: `89 50 4E 47 0D 0A 1A 0A`
- **JPEG**: `FF D8 FF`
- **WEBP**: `52 49 46 46 ... 57 45 42 50`
- **PDF**: `25 50 44 46` (`%PDF`)
